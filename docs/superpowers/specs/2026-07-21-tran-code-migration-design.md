# 按交易码报文迁移设计

## 目标

在现有报文数据迁移功能中新增按交易码迁移模式。用户一次输入多个逗号分隔的交易码和全局每类数量 N，系统按交易码并行执行，从最近五个自然日按近到远的顺序，为 `bzjson`、`sop`、`soap` 三类报文各迁移最多 N 个完整交易。

完整交易指源库 `msg_flow_log_response` 中的响应报文及其同一 `source_ip`、`trans_id` 对应的 `msg_flow_log_request` 请求报文。两张表必须在同一目标库事务中一起写入；缺少请求报文的响应不能单独迁移。

## 范围与口径

- 交易码输入采用逗号分隔，去除首尾空白并去重，保留首次出现顺序。
- N 是本次命令的全局参数，对每个交易码和每种报文类型分别生效。
- 最近五天包括按 `Asia/Shanghai` 计算的当天及前四个自然日。
- 每种类型依次查询当天、昨天至前四天；每天按 `response_time` 倒序选择，直到已选到 N 个完整交易或五天耗尽。
- 从 `tp_online_service_in` 按 `tran_code` 查询全部 `esf_service_code`。去除点号后拼接 `&bzjson`、`&sop`、`&soap`，与源库响应表 `txn_code` 匹配。
- 同一交易码的多个服务码合并后，每种类型合计最多迁移 N 笔。
- 三类报文在五天内均无完整交易，或交易码没有服务码配置时，该交易码分片标记为 `SKIPPED`；它不是失败。

## 架构

复用 `ana_migration_command` 和 `ana_migration_shard` 状态模型，新增命令类型 `TRAN_CODE`。

一个交易码对应一个迁移分片。现有 `MigrationBatchRunner` 用命令并行度限制多个交易码分片的并行执行；单个交易码分片按 `bzjson`、`sop`、`soap` 依次处理，避免为单笔命令创建更多线程和连接。

```text
输入交易码和 N
  -> TRAN_CODE 命令
  -> 每个交易码一个分片
  -> tp_online_service_in 查服务码
  -> 每种类型按五天由近到远选最多 N 个完整交易
  -> 同一事务写 request + response
  -> 汇总迁移、跳过、丢弃和分片状态
```

命令表保存 `tran_codes` 和 `sample_size`，分片表保存 `tran_code`，以便任务详情显示每个交易码及其执行结果。现有时间范围和 SQL 命令的数据与行为保持不变。

## 执行与一致性

- 响应筛选和请求匹配在源库执行，只有成对记录会交给既有批量写入逻辑。
- 目标写入沿用现有按 `(source_ip, trans_id)` 预查的幂等跳过策略；请求、响应写入处于同一个目标库事务内。
- 每种报文类型的数量按完整交易计算。目标已存在的完整交易计为跳过，不补取更旧数据。
- 取消在派发新交易码分片以及切换下一种报文类型前检查。运行中的目标写入批次完成后停止。
- 某个交易码异常时，该分片标记 `FAILED` 并记录错误，其余分片继续。续传只重跑 `PENDING` 和 `FAILED` 分片，`SKIPPED` 不重跑。

## 界面与接口

- 新增 `GET/POST /migration/tran-code-commands` 和对应 Thymeleaf 页面。
- 表单字段为交易码、每类迁移笔数 N、并行度、备注；数据源标签沿用现有 `bxds -> primary`。
- 列表仅显示 `TRAN_CODE` 命令；进度页复用现有页面，并在命令和分片区域展示交易码、N 与分片交易码。
- 扩展取消、续传及进度 JSON 的既有接口，不新增独立任务体系。

## 测试

- 命令创建：交易码解析、去重、参数校验、交易码分片及 `TRAN_CODE` 持久化。
- 运行器：多交易码并行、跳过分片和失败续传。
- 分片执行：服务码展开、三种报文类型、五天由近到远、每类 N 上限、缺少请求报文丢弃、请求和响应事务性写入。
- 页面与控制器：新页面路由、表单和列表内容。
- DDL：新增字段、命令类型和分片状态约束的结构检查。
