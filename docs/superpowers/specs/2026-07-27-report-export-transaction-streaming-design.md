# 报表明细导出交易级流式处理设计

## 目标

将报表明细导出的交易级明细处理改为分片并发、流式读取与幂等批量写入，避免将 `tss_tran_comp` 与 `tss_retcode_comp` 全量加载到应用内存。

本次范围仅包含 `ana_tran_diff_tracking_export` 的生成逻辑；领域汇总和字段级明细保持现有实现。

## 数据读取与并发

- 将 `tss_tran_comp` 划分为固定数量的互斥分片，每个工作线程流式读取一个分片。
- 每个分片查询以 `mesg_seq` 和 `orig_cdate` 左关联 `tss_retcode_comp`，在数据库侧取得响应码与响应描述，避免逐行查询和全量响应码缓存。
- 工作线程以受控批次写入交易级明细，不累积全量结果。
- 交易目录继续作为小型只读缓存，用于补齐交易码、交易名称、领域和负责人。

## 交易级规则

- `comp_result = 4`：两者成功，跳过，不写明细。
- `comp_result = 0/5/6/7`：不使用响应码表。`orig_error_code`、`dest_error_code`、`orig_error_desc`、`dest_error_desc` 与 `field_name` 均写对应状态：
  - `0`：`未比对`
  - `5`：`忽略比对`
  - `6`：`比对中`
  - `7`：`对比异常`
- 其他状态：使用 `tss_retcode_comp` 实际的 528 响应码（`orig_error_code`）和 CCBS 响应码（`dest_error_code`）及描述。
- 成功响应码仅为 `AAAAAAA` 或 `000000000000`。两者均成功时跳过；其他 `field_name` 规则为：
  - 528 成功、CCBS 失败：`528成功ccbs失败`
  - 528 失败、CCBS 成功：`528失败ccbs成功`
  - 两者失败且响应码不同：`二者都失败响应码不一致`
  - 两者失败且响应码相同：`二者都失败响应码一致`

## 幂等与失败处理

- 新增唯一索引：`(source_batch_id, service_code, orig_error_code, dest_error_code)`。
- 使用 `INSERT ... ON CONFLICT (...) DO NOTHING` 跳过重复问题明细。
- 各分片使用独立数据库事务以支持并发。任一分片失败时，协调器等待其他分片结束，删除该 `source_batch_id` 已写入的交易级明细，并使任务失败，避免保留部分结果。

## 验证

- 覆盖四种状态行、成功/失败响应码组合、两者成功跳过和响应码为空的场景。
- 覆盖重复问题在同一批次只保留一条。
- 覆盖并发分片处理后无重复数据及失败清理。
- 覆盖大于单次写入批次的数据量，确认处理不会全量聚合到内存。
